## 1. How we work (process rules)

- **Every code change goes through a PR before `main`** (standing rule, 2026-07-12). Direct
  push only on an explicit per-change waiver. "You may commit" authorizes a commit, **not** a
  push. **Doc-only carve-out (2026-07-13; push extension 2026-07-26):** markdown-only diffs
  (`docs/`, `thoughts/`, READMEs) skip the PR — commit on `main` and push directly (the
  owner-pushes step is retired for doc-only diffs).
- **RPI workflow** (research → plan → implement) for non-trivial features; the plan is the
  human-review gate. Two concurrent features: plan both first, compare footprints. Details in
  `CLAUDE.md`.
- **`Box_Setup_Stuff/` is not documentation — it's the only context a host-side Claude gets**
  when bootstrapping/maintaining trades-box-1. It cannot see this repo. So: (a) any
  architectural change to the agent stack must update `Box_Setup_Stuff/` in the same change;
  (b) those files must be self-contained — never "see docs/X §N", always inline the fact.
- **Verify vendor claims against live docs, cite URLs** (`CLAUDE.md` has the rule and the
  Composio case study).
- **Never paste badge plaintext anywhere** (chat, docs, commits). A 2026-07-03 leak forced
  rotating every badge. Fingerprints (sha256) only.
- **Concurrent sessions share a checkout at their peril** (2026-08-15): a `git commit -a` in one
  session sweeps the OTHER session's in-flight working-tree changes into an unrelated commit
  (live case: 8830e46 "query_spine window warning" silently included the money-ledger session's
  half-edited `server.ts`). The CLAUDE.md worktree rule exists for parallel /implement runs —
  apply it to ANY two sessions that might touch code on one branch, and prefer `git add <paths>`
  over `-a` when another session may be active.
- **A new table that references ONLY `tenants` escapes every cleanup cascade** (2026-08-15,
  firm-profile review): the eval world reset, `seed.mjs`'s truncateSpine, and the test-suite
  truncates all clear spine tables and let `cascade` catch dependents — but they deliberately
  keep `tenants`, so a table whose only FK is `tenants(id)` (e.g. `tenant_profiles`) is reached
  by nothing, silently survives every "clean rebuild", and (FK NO ACTION) makes
  `delete from tenants` fail 23503 on the next eval-world rebuild. Adding such a table means
  adding it BY NAME to `scripts/spine-eval/world.mjs` RESET_TABLES, `scripts/seed.mjs`
  truncateSpine (existence-probed — hosted may lag on migrations), and the relevant test
  truncate lists.

## 2. Product principles (user decisions — don't re-litigate, do cite when relevant)

- **Agent-first framing + the intelligent-spine direction** (2026-08-15, user decision): the
  product is the **harness and context-management engine for a fleet of AI agents** serving a
  trades firm — agents are the entire interface, the spine is their shared memory, the harness is
  what makes their output trustworthy. "One record every role reads and writes" is the same
  system described data-first; the agent-first framing is now the front door (onboarding §1,
  overview §2). DIRECTION (nothing built): make the spine itself intelligent — a spine-side
  "team leader" agent that monitors the flow, detects gaps via deterministic watchers (e.g.
  visit time passed, no status update), and proactively prompts the right person's agent to fill
  them; passive intake → active gap-filling → eventually anticipation. Constraints ratified with
  the direction: detection is deterministic (hardcode-vs-model rule), the team lead is a NEW
  identity class that may only **read/ask/stage — never commit irreversible or externally
  visible actions** (it has no human to confirm), nudges are budgeted (over-pinging = the
  over-confirmation failure mode — **the numeric budget was REVERSED 2026-08-18, see "Nudge
  frequency is paced by urgency, never capped" below; the anti-spam GOAL stands, the counter
  does not**), and agent-to-agent communication stays spine-mediated.
  **Transcript-harvest disclosure ratified** (2026-08-15): workers must be told up front that
  chats with their company-provided agent can be recorded to the firm's record (extends the
  2026-07-04 outbound-send disclosure); the work-relevance classifier gates HARD before anything
  harvested reaches L1 — no contamination of the spine with non-work context, no new exception
  to classify-before-insert. **Plan-review decisions (user, 2026-08-16):** watchers land BEFORE
  money-inference (its quiet-jobs nudge becomes the framework's second detector); watcher v1 =
  overdue confirmed visits, 72h look-back confirmed; cron pulse → `*/5` minute-gated (steps 1–7
  stay quarter-hourly, watcher every tick); **escalation ladder = at most TWO touches per gap —
  technician's agent first, dismissed/unanswered → manager, never a third** — and the asking
  agent follows up until the gap is VERIFIABLY filled (a capture lands — the deterministic
  activity-after-end check, not model judgment). Direction doc:
  `thoughts/shared/plans/2026-08-15-intelligent-spine-direction.md`.

- **Nudge frequency is paced by URGENCY, never capped** (2026-08-18, user decision —
  REVERSES the 2026-08-16 "2 asks/person per rolling 24h"). The product is an AI manager/
  teammate, and an agent is only as good as the information it gets. Trades operators will not
  reliably volunteer that information, and cannot be expected to know which information the
  agent actually needs — so the agent must ASK, actively and often, and asking is also how user
  behaviour gets trained. A per-person counter throttles good and bad questions identically and
  "fundamentally puts a bottleneck on how efficient humans and AI can work together" (user).
  Solo contractors — the target segment — should expect frequent daily contact. Replace the
  counter with the way a good human teammate actually behaves:
  - **Earn the ask — but derivability is DECLARED PER GAP KIND, never re-litigated per
    question** (refined 2026-08-18, same session). A blanket "think before asking" burns tokens
    on gaps that are structurally underivable, and once contact is frequent the human is a
    CHEAP, high-accuracy oracle — asking is often the efficient choice, not the fallback. So
    every detector declares one of three classes at design time:
    **(a) `ask`** — the answer exists only in a human's head (what the parts cost, how the
    visit went). Straight to the human, ZERO derivation, zero tokens. Expected to be the
    common case.
    **(b) `derive`** — a deterministic SQL/code predicate can resolve it; run that first and
    ask nothing if it resolves. Costs ~0 tokens and is where the real value sits. Precedent
    already shipped: the watcher's activity-after-start "filled" check suppresses asks with
    pure SQL.
    **(c) `attempt`** — a BOUNDED model attempt is worth it before asking (the money-inference
    shape). Highest cost, least certain; use sparingly and cap the effort — an unbounded
    derive-first is worse than the question it was avoiding.
    A question is a last resort only within class (b)/(c); in class (a) it is the FIRST and
    correct move. This is a precondition on each ask, not a limit on their number.
  - **Urgency sets latency, not permission.** Every gap kind carries an urgency; urgent gaps
    interrupt immediately, routine gaps trickle out across the day. Nothing is dropped for being
    unimportant — it is merely slower.
  - **Batch the unimportant.** Low-urgency gaps ride together in one message ("three quick
    things"), which is what makes high volume feel like a colleague rather than a stream of
    pings.
  - Unchanged by this decision: the two-touch escalation ceiling, the 7am–7pm firm-local ask
    window, once-ever-per-subject dedup, and the per-tenant per-tick surge brake. Note the
    runaway-detector risk the old cap incidentally covered now needs a per-detector sanity
    guard — a misfiring watcher is a bug, and a per-person counter was never the right place to
    catch it. **Code state 2026-08-19:** the counter is GONE (PR #153 — `NUDGE_BUDGET_PER_PERSON_DAY`,
    `countRecentAsks` and `BUDGET_HOLDING_STATUSES` all deleted; tests 1790 -> 1787, no behaviour
    change since the cap was not the binding throttle). The per-detector runaway brake LANDED with
    detector #2 (PR #155): every spec in `NUDGE_KIND_SPECS` declares its own `maxNewPerTenantTick`
    (`overdue_visit_gap` 5, `job_cost_gap` 3), spent against the shared per-tenant per-tick ceiling
    so a second detector cannot raise a firm's volume. The urgency/batching design (pacing by
    urgency, carrier/rider batching) is still NOT built. **Reframed 2026-08-23 (user ruling):
    it never will be built as machinery — judgment-based pacing IS the planner's job.** The
    planner already sees every open gap, its age, and who was asked what, and decides
    ask/extend/escalate each tick; a deterministic pacing engine beside it would re-solve the
    planner's problem in code (the same distrust-of-the-model layering the one-call collapse is
    retiring). Earn-the-ask / urgency / batching live as planner-prompt doctrine and as lessons
    the Reflector can propose from gap_summaries; whether pacing is GOOD is measured by the
    agentic eval at scale, not enforced by a counter. The only code that may remain is
    delivery-level batching tooling (the carrier/rider mechanics — one combined message for
    several gaps, each rider getting its own `asked_at`): the planner decides WHAT to batch,
    code only carries it. "Pacing replacement RPI" is off the debt list.

- **The spine is not the books** (2026-08-15): the money layer is an evidence-linked money
  MEMORY reconciled against the firm's real books, never presented as the books. Precision over
  recall — a missing number is an honest gap ("no payment on record"), a wrong number is a
  trust incident. Writes are evidence-class-tiered: spine-performed actions record themselves
  as fact; the manager's own outbound artifacts (an email THEY wrote) auto-record with
  immediate disclosure and an auto-record cap; everything else (notes, inbound, transcripts)
  only ever becomes a QUESTION — the ledger gains the entry when the manager confirms. Money
  reads must attribute figures to their evidence ("from your email Tuesday"), never assert
  balances as fact. Accounting-GRADE numbers come from ingesting the firm's own money system
  (part D direction, thoughts/shared/plans/2026-08-15-accounting-ingestion-direction.md), after
  which inference demotes to job-linkage; inference remains the bridge for unconnected firms
  and the only path cash ever takes (field notes).

- **The money layer is workflow-agnostic — never pilot-fitted** (2026-08-15, user decision,
  research stage; nothing built). Firms genuinely diverge in how price and payment flow
  (estimate-first vs just-fix-it, deposits vs none, one invoice vs progress billing, on-site
  vs back-office vs external/QuickBooks invoicing, single payment vs partial payments vs
  financing vs write-off). The pricing/invoicing/payment design must be able to *represent
  most of these chains*, not encode the pilot firm's practice or our guess at a canonical
  flow. Pilot-firm answers are validation data points, not design inputs. Research +
  consequences (including the conflict with the linear `job_status` tail
  `completed → invoiced → paid`, which hard-codes exactly one chain):
  `thoughts/shared/research/2026-08-15-pricing-invoicing-payment-loop.md` (see its addendum).
- **Telegram is the entire UI** (2026-07-03). No web front end exists or is planned. Managers
  and technicians do everything through their Telegram agent chat; the Telegram **Mini App
  dispatch board** (2026-07-14) is the one recorded, deliberate extension. **Evolved
  2026-07-23 (user decision):** the board is no longer view-only-plus-gestures — it is *the
  manager's hands* for quick direct edits (a manager already in the Mini App won't exit to
  chat and come back); the agent's role is **autonomy + recommendation** (propose/solve/
  confirm/nudge). Non-negotiable guardrail: every board gesture calls the same
  `src/schedule/booking.ts` verbs as chat — one write path, one promise-ladder gate, never a
  parallel editing logic. Operators (us) appear only at initial setup and breakage; anything
  else operator-side is debt to automate.
- **A schedule READ renders the booked order; it never re-derives one** (2026-07-31, user
  decision). `get_schedule` used to ask Google Routes for the "best driving order" and return
  the technician's day re-sequenced — contradicting the times the customers were promised and
  the order the board shows, from a tool that changes nothing and cannot move anything.
  Removed. Both schedule reads now return stops in booked (time) order, and **each stop carries
  its own destination-only `mapsUrl`** instead of one multi-waypoint day link (no 10-stop cap,
  no truncation, and it matches how a day is actually driven — navigate to the next stop, not
  the whole day at once). **Links belong to a PERSONAL route view only** (user decision
  2026-08-03, from live evidence): `get_team_schedule` briefly carried them on the caller's own
  stops and they were removed before merge — that read is a TEAM view by construction, and a
  manager asking "what's on the schedule this week" is dispatching, not driving, so directions
  to their own couple of stops answered a question nobody asked. Corollary worth keeping: the
  right question for a result field is not only *is it correct and correctly scoped* (it was
  both) but *does it belong in the answer to what was actually asked*. A manager's own driving
  day is the board's job. The dividing line to keep: **deciding order means MOVING
  visits** (promises, confirmation, a DB write) — that is `run_freeze`/`run_resolve`'s job, and
  a read must never do it quietly. Upstream fact this rests on: *"Waypoints are displayed on
  the map in the same order they are listed in the URL"*
  (https://developers.google.com/maps/documentation/urls/get-started).
- **Vocabulary must track what actually gates** (2026-07-23, PR #74). `assignments.locked`
  marks a manual placement for the *future* auto-scheduler (Plan 4b) to route around — every
  manual book/move stamps it true, so a "locked" badge appeared on every visit and read as
  "this time can't change" (false: no-promise visits move freely, one-shot). The badge is
  gone; the **promise ladder** is the human-facing constraint vocabulary. Don't surface
  solver-internal flags to humans until the solver exists; when 4b lands, `locked` can
  resurface as "pinned — won't be auto-moved".
- **Two access tiers, `manager` and `technician`** (2026-07-02/04). Technician = broad
  non-manager catch-all (field techs, office, sales). Manager seats price higher and get the
  **entire Composio catalog + self-serve pairing** (risk accepted deliberately — no structural
  block, disclosure + confirmation instead). Technicians get a curated tool list; technician
  email sends go through the spine's two-step `send_email`, never `GMAIL_SEND_EMAIL`.
  Enforcement point = per-person Composio **session** configs (execution-enforced, verified:
  HTTP 400 code `4310`, not 403) + doorman badge tier for spine tools.
- **Seat-based licensing** (2026-07-02): a firm buys N seats; adding a person needs a free
  seat (structural server-side cap, never trusted to the agent). All purchased seats'
  sandboxes are **pre-built cold** (hardware up, identity empty). Seats are reusable;
  **technician refs are permanent and never reused across humans** (L1 is append-only).

### The sweep is more permissive than the planner is instructed to be (2026-08-21) — FIXED 2026-08-22

> **RESOLVED by the 2026-08-22 plan (`thoughts/shared/plans/2026-08-22-the-brain-can-attribute.md`).**
> The `close` half below is now HISTORY: `spec.filled` no longer closes an ASKED gap at all, so the
> race it describes cannot happen and `close` is the normal way an answered gap ends. Kept because
> the *diagnosis* is the reasoning behind that plan, and because the `send`/`hold` half still
> stands. Two things a reader must carry forward:
> - `filled` still closes a gap **nobody has been asked yet** (the pre-ask carve-out) — that is the
>   detector re-checking itself, not a judgment, and removing it means asking a technician at 7am
>   about a job they reported at 8pm.
> - The sweep keeps a **fail-safe** at the escalation deadline for a planner that has gone silent
>   for a working day. It declines when the job carries more than one open gap, because `filled`
>   is job-keyed and cannot tell which question a note answered.

Found while closing out Phase 4, and it makes two of the planner's four actions
near-unreachable in production.

**Ordering.** In one lifecycle run: watchers+sweep (step 8) → planner (step 9) → compose (step 10).
The cron is `*/5`; the planner self-gates to `%30 < 5`. So the sweep sees everything six times more
often than the planner does, and beats it within a tick.

**`close` is unreachable.** *(No longer true — see the resolution note above.)* The sweep auto-resolves on `hasActivitySince(jobId, …)` — ANY
job-stamped capture or new visit row. Any evidence the planner could cite has therefore already
closed the gap. **And the two disagree about what counts:** the sweep closes on any activity, while
the planner's prompt says *"Activity on the job is not an answer: a note about something else, a
status change, a visit being logged, or somebody promising to write it up later — none of those
fill the hole."* The code is looser than the model's instruction, and the stricter judgment can
never apply because the looser path always arrives first. Consequence: `assert-only-cited` guards a
path that essentially does not execute, and gaps close on activity that may not answer the
question — the exact failure the prompt warns against.

**`send`/`hold` are rare.** Both write `not_before`, which gates COMPOSE only. Compose drains
pending rows every 5 minutes, so a `pending` row is visible to the planner only on a tick where the
watcher just minted one (same-tick birth IS seen, given the step ordering) or on the first tick of
the morning, when overnight rows accumulated because compose held them and the planner skipped the
ask window.

**So the planner's LIVE vocabulary is in practice {escalate, leave alone}** — which matches the only
live decision observed so far. Worth confirming against a fuller `nudge_decisions` corpus before
treating it as settled, and worth remembering before anyone tunes the planner's judgment about
closure: today that judgment mostly cannot reach the row.

### A delegated action needs its performer's gate (2026-08-21)

Found by reading the planner plan's four phases **together** rather than one PR at a time — a
cross-phase pass after every phase had already been reviewed on its own and an independent
whole-PR review of Phase 4 came back clean. Neither could see this, because no single diff
contains it.

**The shape.** Phase 4 made `escalate` *delegate*: it does not escalate, it writes
`escalate_after = now` and lets the sweep perform the handoff, so the rung-2 flag and the orphan
doctrine stay in one place. Phase 3 had separately, and deliberately, decoupled the planner's gate
from the ladder — `PLANNER_MODE` alone, never `NUDGES_MODE`. That decoupling reasoned carefully
about a NUDGES_MODE rollback and never mentioned `WATCHERS_MODE`. But the sweep reads open nudges
only when the watcher is live (`watchers.ts:361`), and step 8 is skipped outright when the var is
unset.

So `WATCHERS_MODE` ∈ {unset, shadow} with `PLANNER_MODE=live` gave: the deadline write succeeds,
`applyDecision` correctly reports `applied` because a row really moved, the decision log records an
escalation — and no manager is ever told. **Void is survivable; void-and-logged-as-delivered is
not**, because the one place anybody would check says the handover was made.

**The rule.** When an action is performed by a different component than the one that decides it,
the decider must be told whether the performer is running. The planner now takes `sweepLive` from
lifecycle and refuses `escalate` without it — the same rail as the `send`/`hold` status checks, one
level up: there an action is refused because the ROW cannot observe it, here because the DEPLOYMENT
cannot. Refused, not skipped, and the reason says the machinery failed rather than the judgment.

**Also fixed in the same pass:** the prompt's WHEN TO GIVE UP paragraph told the model that an
already-escalated, still-unanswered gap should be closed. Closing requires a quote to cite or a
filled record, and an unanswered gap has neither — so the instruction could only ever be refused.
It was harmless while the planner had no memory; **Phase 4's history line made it reachable**, since
an applied-but-not-yet-swept escalate renders as `prior decisions: 1 (last: escalate, …)`. A
capability added in one phase can activate dead prompt text written in another — re-read the prompt
against the rails whenever either changes.

### Continual learning — direction, and the finding that changes the obvious fix (2026-08-20)

**User direction, recorded as direction (mostly out of current scope):** we eventually want
**continual-learning frameworks** for the team-lead planner *and* the technician/manager agents.
The planner is the natural first host — it runs once per 30 minutes, so it can afford to think
longer, carry a bigger context, and possibly run a frontier model. Full literature record with
citations: `thoughts/shared/research/2026-08-20-continual-learning-for-the-planner.md` (three
AI Engineer / Sequoia talks, Aug 2026, plus ACE arXiv 2510.04618 and the experience-reuse study
arXiv 2604.27003).

**Do not build "feed it the logs".** Measured (arXiv 2604.27003): raw trajectories as the memory
unit give **NEGATIVE** forward transfer (−9.5% / −7.5%); ~3 **abstracted insights per episode**
give **POSITIVE** (+6.5% / +9.0%). Raw traces are worse than no memory at all. Three companion
cautions, all measured or named in the literature:

- **Homogeneous memory collapses retrieval** — 88.5% of queries returned the same item, 5.4% of
  entries ever read. A planner decision log is maximally homogeneous (`hold, hold, hold`), so any
  reuse must be **scoped to the gap**, never a global similarity pool.
- **Context collapse / brevity bias** (ACE) — a model iteratively *rewriting* an accumulated
  context erodes it. Correct shape: itemised entries + incremental delta updates merged by
  **deterministic non-LLM code**. Needs no labelled supervision; natural execution feedback is
  enough.
- **Hint leakage** (on-policy self-distillation) — never put the outcome into a replayed context.
  This is the trap any future planner replay-eval will hit.

**Framing to reuse (Yu Su):** *intelligence* = reasoning through an unfamiliar problem from
available context, every episode independent; *expertise* = accumulated situated competence.
"Intelligence solves the problem given the context; expertise brings the right context."
Intelligence expands search, expertise compresses it. Scaling IQ alone produces **"the world's
smartest novice"**. And modern work is **millions of micro-worlds** with their own local physics —
every trades firm is one, which is the strongest outside statement of this repo's thesis.

**Model choice — answered, and the answer is "not yet".** The planner's observed failures are
context and vocabulary failures, not reasoning failures: it whiplashed send→escalate inside 30
minutes because it had no record of its earlier decision, and it reached for `send` on an
already-`asked` row because no "ask again" action exists. A stronger model with the same amnesia
makes the same mistakes. Fix context and actions first, then re-measure — noting we currently
**cannot** measure it, because there is no planner eval. `scripts/date-eval/` is the proven shape
for one (real traffic, graded through the real harness, mechanical adjudication).

**We fail traceability today.** Planner decisions go to `console.log` plus the lifecycle stdout
JSON and nowhere else — nothing is persisted, so every tick's experience is discarded and no
corpus exists for any of the above. Two harness rules from the same talks that our code should be
held to: **make tool responses informative** (a tool returning `done` leaves nothing to learn
from — and it is exactly why a `send` on an asked row would be a silent no-op), and the real
feedback signal is **edits, undos and retries**, not thumbs up/down. Lessons also carry a
**pertinence tier** — globally-true → weights, per-org/per-user → context; we own no weights, so
everything lands in context, but the tier still has to be recorded or per-firm quirks leak across
tenants.

**The design framing that came out of it (2026-08-20, user ratified).** Five rules, in the order
they bite:

- **Push the keys, pull the content.** Injecting literal history into every prompt does not scale;
  telling the model to "go look" fails when it does not know a fact exists. Keys cannot be guessed,
  so they are pushed; content is fetched. Proof from this system: the planner searched
  `customer_name LIKE '%Okafor%'` and burned turns on nothing — the fix was pushing the job id.
  **You cannot prompt your way to a UUID.** The gap id and job id are already in the prompt;
  `customer_id` is NOT, so any customer-level memory repeats the trap until it is.
- **Only accumulate what something can later falsify.** The line between memory and drift. A gap
  decision has a built-in check (did the hole get filled); a free-form "picture of the customer"
  has none, so a wrong entry is never corrected and feeds the next tick. "Pays 30+ days late"
  (money ledger) yes; "the tech seems frustrated" no.
- **Traces are not memory.** Tool calls and full reasoning are raw traces — the measured-negative
  thing to feed back. Store them for us (eval, debugging, a future Reflector); the planner reads
  distilled entries only.
- **Append-only, never model-rewritten.** ACE's context collapse is exactly a model iteratively
  rewriting its own accumulated context. Add entries; never edit or delete.
- **Keep it out of the record.** Agent-inferred memory is the weakest evidence class and must not
  live in L3 `attributes`, which `get_job` renders to managers as business fact.

**Verified state of tracing, 2026-08-20: there is none.** `runToolLoop` returns `calls[]` (name,
args, result) and `planner.ts` uses `.length`; the rest is discarded. `recordModelUsage` writes
COST events only — tenant + technician_ref + sku + tokens, no job, gap or decision. Spine reads
write no L1 capture. Nothing can point a batch of tool calls at a decision about a job.

- **Field notes record one-shot; standing facts still confirm** (2026-08-21, user decision —
  **SHIPPED**, plan ② Phase 2): `record_field_note`'s two-step confirm is GONE for a customer or
  job that already exists. It survives in exactly one case, and that carve-out is load-bearing:
  an answer that would **CREATE a customer** still previews, on the first call and on the
  identity resume alike, because the revertability argument below does not reach it — a note can
  be retracted by its author, but a customer pinned by a stamped capture cannot be removed at
  all. Answering `needs_identity` records: a missing datum was never a confirmation. One-shot
  writes carry a content-hash `external_id` over tenant, technician, channel, customer, job,
  text AND blobPath — a note can be a photo with no text, and a hash collision on an append-only
  table means a note silently, permanently missing. A repeat answers `duplicate`, never
  `recorded`. The original reasoning: The confirm was justified by "L1 is
  append-only", but that reads the constraint too literally: `retract_capture` never deletes and
  yet the **fold** drops the capture, its visit, and any standing fact citing it from every
  consumer read *by construction* (`src/db/context.ts:75-78`) — and **"only the capture's author
  or a manager may retract"**, so the technician can undo their own note unaided. A wrong note is
  therefore functionally revertable, which puts it squarely under the ratified confirmation-tone
  doctrine (confirm only the irreversible or externally visible; reversible = do it and say what
  you did).

  Note the confirmations currently sit on the wrong side of the asymmetry: recording a note is
  additive with no fan-out, while **retraction cascades** — it silently removes visits and
  standing facts, which is why it stages a `willAlsoRemove` preview. Same ceremony, opposite blast
  radius.

  **Scoped to field notes.** `record_standing_fact` KEEPS its confirm: a standing fact lands in
  every future briefing, so a wrong one propagates until somebody notices. Two things retraction
  does not cover, for the record: side effects the note caused (e.g. a job status change) are not
  auto-reverted, and audit-channel captures (`outbound_email`, `agent_action`) are manager-only to
  retract.

  Motivating specimen (2026-08-19): one technician message answered a visit gap and a money gap.
  The money committed instantly (one-shot), the note became an *offer* — so the reply opened with
  "Recorded!" and then asked permission, telling the technician they were done when they were not.
  The agent never even called `record_field_note`; there was no staged note to say yes to.

- **A mixed batch confirms as a whole** (2026-08-21, user decision): when one message produces
  writes of differing confirmation levels, the batch takes the STRICTEST — nothing is recorded
  until one yes covers all of it. This kills the two-states-in-one-message failure above.
  **Adoption order is load-bearing:** remove the field-note confirm FIRST. The batch rule alone,
  with field notes still confirming, would have held the Aug 19 money event behind a yes that
  never came — losing the $500 that today at least lands.

  **Recording is atomic; undo is NOT, and must not be forced to be.** One confirmation can produce
  three records with three different undo paths:

  | record | undo | shape |
  |---|---|---|
  | field note | `retract_capture` — folds the note **and its visit** | L1 fold |
  | standing fact | `retract_capture` on its OWN capture (`externalId: fact:<confirmId>`) | L1 fold |
  | money event | a voiding/correcting ledger entry (`correctsEventId`) | ledger, not a fold |

  Verified: none of these cascade to the others. The fact mints its own capture at commit
  (`server.ts:3388`), so note and fact never cite each other; and money is untouched twice over —
  the dispatch never passes `sourceCaptureId` (`server.ts:5479`), and nothing folds money anyway
  (`context.ts` does not mention it). **Do not "fix" this by folding money** — a ledger corrects
  by adding a reversing entry, never by hiding a row; a read-time fold would make the books
  disagree with themselves.

  The gap to close is that the records do not know they were born together. Design direction for
  the Group A plan: **stamp one batch id into everything a single confirmation produces** (note
  capture metadata, fact capture metadata, money event `detail`) so a retraction can look sideways
  and OFFER the siblings per item rather than silently leaving them. The hook nearly exists — the
  fact's capture already stamps `stagedConfirmId`, but it points at that fact's own token rather
  than a shared one. This also closes a standing provenance hole: **money events currently record
  no link to the message that reported them at all.**

### The person we ask may not know, or may not have been there (2026-08-21)

User direction, while reviewing the manager copy:

> "we need to accept that sometimes the technician is not a qualified source to answer a question"
> … "they might even get replaced by another technician for a job without us knowing, then we'll
> probably be forced to escalate to resolve the gap"

The ladder currently treats every unanswered ask as silence to be chased. Two cases are not that:

1. **Wrong question — and we cannot tell which firms it is wrong for.** The cost detector asks
   *"what did the job cost in parts and materials"*. Sometimes the technician has no idea: the
   price is on an invoice the office holds and they never see it. **Sometimes they know it better
   than the manager does** — they negotiated on site, added services, took payment on the spot
   (user, 2026-08-22). Which one a firm is depends on how that firm operates, and nothing in the
   spine knows. So an earlier draft of this section asserting "it is on an invoice the office
   holds" was wrong, and the planner prompt repeated it to a manager as a fact about a specific
   job before the eval caught it (see below).
   The safe conclusion is narrow: **do not assume who knows.** A question like *"what parts did
   you put in?"* is answerable by any technician regardless of which kind of firm it is, which is
   why it is the better ask — not because the office holds the price. Flagged, **not built** —
   deliberately kept out of plan ② to avoid widening it.
2. **Wrong person.** A job's technician can be swapped in the real world with nothing telling the
   spine. The person being chased was never on site. Their silence is correct behaviour.

**Consequence.** Escalation is not only a failure path — when the respondent cannot answer, handing
the gap to a manager IS the right resolution, and no copy or metric may frame it as the technician
having ignored us. (Same reasoning that deleted "hasn't heard back" from every manager template in
plan ②: we have no reply-side datum, and would not be entitled to that conclusion if we did.) Any
future answer-rate metric must separate *could not answer* from *did not answer*, or it reads a
routing problem as a compliance problem.

### The manager's bucket has never drained (2026-08-21)

Live audit of the pilot: **80 open review items, and not one has ever been resolved or dismissed** —
77 stage-0 visit items, 3 escalations, 0 cost items. A visit item auto-closes as soon as any
activity lands on its job, so 80 sitting open means nothing ever landed on any of them.

User's design for Group B, **not yet built**: batch the open items and have the planner send a
one-click "record all" near the end of each working day, rather than surfacing them one at a time
(spam) or letting the bucket grow unbounded. Gaps the planner judges urgent still surface alone.
The asymmetry to design around: only MONEY items can be one-click, because only they have a figure
sitting in a note waiting to be promoted — the visit items in the bucket have nothing to propose
from, so for them "batch" can only mean batch-re-ask or batch-dismiss.

### The layering is a capability assumption, and it is expiring (2026-08-22)

Much of the ladder's stage-splitting — detector, planner, compose, sweep, each its own model call
or none — was absorbed while the agent stack ran GLM-5.2: runaway reasoning, 4096-token
truncation, a 13-deep tool schema turning a 3-second turn into 67. Those are claims about what a
model can hold, and they do not survive a frontier planner.

This repo's own measurement says the same thing from the other side: the date eval went
**86 → 97 → 100% on the SAME model**, and every gain was a context fix (`upcomingVisits`,
server-side counts, `windowCoverByDay`, served phrases, a clock warning). The recorded conclusion
is that our failures are **context and vocabulary, not reasoning**.

**User direction, 2026-08-22:** memory architecture (Group C) FIRST, then the fixture-spine agentic
eval at scale — running it earlier would measure a planner re-investigating from scratch every 30
minutes, which is not the system we intend to ship. Then collapse investigate/plan/compose into one
model call.

**The collapse is a COHERENCE play, not a cost one.** `runTeamLeadCompose` calls the model once per
PENDING nudge, and a nudge is composed once before it becomes `queued` — so volume tracks gap
creation (~5/day for a small firm) against the planner's 24/day. The defect worth fixing is that
the decision and the wording never meet: compose cannot see that this is a third ask, or that the
planner judged it urgent. Only a timestamp crosses between them.

Two properties must be given up deliberately rather than discovered:
- **Independent rollback of the technician-facing voice.** Compose is gated on `NUDGES_MODE`, not
  `PLANNER_MODE`, so today the ladder still speaks with the planner switched off.
- **Per-gap failure isolation.** One call for N gaps means one timeout affects N; today a compose
  failure costs exactly one gap, which hands to the manager.

### What the planner-copy eval does and does not measure (2026-08-22)

`scripts/planner-eval/` renders scenarios through the REAL `buildGapView` and
`buildPlannerUserMessage` out of `dist/` — the `doctrine.ts` rule one layer up: an eval that
hand-writes its own gap blocks measures a prompt we do not ship.

It gives the model **one forced `submit_plan` call and no read tools**. Production hands it
`spine_read`, `recall_decisions`, `get_customer_context` and `resolve_date` inside `runToolLoop`.
So it measures *"given context already gathered and laid out, does it decide and write well"* —
never *"does it find what it needs"*. First run: 9/9 deterministic copy checks, and the judge
caught the planner asserting *"the figure may sit on an invoice the office holds"* — prompt
guidance surfacing as a fact about a specific job, which a planner with no way to look anything up
has to guess at.

**Cost shape, measured:** OUTPUT was **52.4%** of the bill, uncached gap blocks 30.3%, and the
cacheable prefix — all caching can touch — **17.3%**. A "90% saving from prompt caching" quoted
without that split reads far bigger than it is. And the planner's 30-minute cadence means the
DEFAULT 5-minute TTL is cold on every call: it pays the 1.25× write and never reads, which is worse
than not caching. Only `ttl: '1h'` wins in production, and that rests on a cache read refreshing
the TTL — unverified, because seconds-apart eval calls cannot test a 30-minute gap.

**Deploy/migration gotchas (each one burned us):**
- Render's **"Redeploy" button re-runs the OLD commit** — use "deploy latest commit" and
  confirm the **live commit hash** in the dashboard. Two E2E attempts once failed on stale
  server code this way. The API is the same trap: `POST /v1/services/{id}/deploys` with no body
  redeploys **whatever is already live**, and the MCP `trigger_deploy` reports that old commit
  back to you (observed 2026-08-20 — it returned #157 while main was two commits ahead).
- **A CRON service cannot be deployed by commit id at all.** `POST /v1/services/{id}/deploys`
  with `{"commitId": …}` answers `400 cannot deploy cron job service … by commit reference ID`.
  So for `lifecycle-heart` there is NO "ship this specific commit" escape hatch: it is
  branch-head via webhook, or a redeploy of the live commit. **If a webhook is genuinely
  dropped, the only fix is another push.** Normal webhook latency is ~16s (measured); one
  2026-08-20 push sat >6 minutes with no deploy record created at all, so do not assume slow
  means stuck — but do not fire `trigger_deploy` at an autoDeploy service either, it only
  rebuilds what is already running.
- **Nothing auto-applies DB migrations to the pilot.** Render only builds+starts.
  `npm run db:push` is unreliable here — the pilot's migration ledger has drifted from the
  repo (versions applied that no repo file carries). Use the Supabase MCP `apply_migration`
  for pilot DDL. Ledger reconciliation = open tech debt.
- **Deploy-before-migration** fails safe but noisily (PostgREST "unknown column" on the new
  code path; fix = apply migration + `NOTIFY pgrst, 'reload schema'`). Happened live
  2026-07-19 (seat-exempt); the two-step confirm flow protected the pilot.
- **A new tool surface silently bypasses whatever doctrine rule did not name it — twice now.**
  Tool search broke §0f by making `resolve_date` something the model had to *find* (fixed by §0j,
  then reverted with it). `query_spine` broke the same rule a different way: on its first live turn
  (2026-08-06) the agent wrote `local_day >= '2026-07-07'` straight into SQL with no `resolve_date`
  call — correct by luck. Harmless for a count; the identical shape on "what's booked next week"
  is the 2026-07-25 week-boundary incident, which missed a real visit.
  **The durable fix is to stop enumerating tools in doctrine.** §0f rule 2 said "never hand a
  YYYY-MM-DD you calculated to book_visit or move_visit" — a list, so anything not on the list was
  implicitly fine. It now reads "to ANY tool … if a date reaches a tool, it came out of
  resolve_date", with the SQL case named explicitly. The `query_spine` description carries the
  same rule fused in, and `src/mcp/server.test.ts` asserts that text so it cannot be edited away.
  **When adding any tool that takes free-form input, re-read the doctrine blocks and ask which of
  them name tools rather than behaviours.**
- **Bake derived values into the views; the agent computes anything you leave out, and gets it
  wrong (2026-08-06).** `v_schedule` had `local_day` but no weekday. Asked "how many visits did Joy
  do this week?" the agent did everything the previous fix required — `resolve_date {week:0}`
  first, its boundaries pasted into the SQL, 22 visits, verified correct — then reported *"running
  from Monday the 4th"*. **2026-08-04 is a Tuesday.** §0f requires stating the weekday whenever a
  date is named, so with none to read it derived one. The count being right is what makes it
  dangerous: nothing in the answer looks suspicious.
  Fixed by adding `local_weekday` (`to_char(…, 'FMDay')`; FM suppresses Postgres's blank-padding)
  beside `local_day`, plus a description line to select and relay it verbatim. Tests guard the
  column and the description text.
  **`CREATE OR REPLACE VIEW` may only APPEND columns** (42P16 "cannot change name of view column");
  inserting one mid-list needs DROP + CREATE — atomic inside a migration, re-grant afterwards.
  **The pattern, four for four in three days:** tool search hid `resolve_date`; `query_spine` let
  dates be written straight into SQL; a view handed over a bare date; and then `resolve_date` itself
  turned out to hand over bare dates for week RANGES. Each fix was correct and each exposed the next
  gap. Generalisation worth carrying: **any value the model must derive in order to answer well is a
  value it will eventually derive wrong — put it in the data, not in a rule telling it not to.**
- **`local_weekday` did not close it — `resolve_date` week ranges were the real hole (2026-08-06).**
  The re-test after shipping `local_weekday` looked like a pass: "Joy has 22 visits this week
  (Mon Aug 3 – Sun Aug 9)" is entirely correct. It was still derived. The agent's SQL was
  `select count(*) … where local_day between …` — it selected no weekday column at all, so
  `local_weekday` never entered the answer. **A view column can only help when the agent names a
  date it SELECTED; the dates in that sentence were the WINDOW's boundaries, and those come from
  `resolve_date`.** Naming the window is by far the commoner shape, so the fix was aimed one layer
  off. `ResolveDateResult.resolved` had carried a `weekday` since day one; `resolved_week` returned
  `{weekStart, weekEnd}` and nothing else.
  Fix: `weekStartWeekday`/`weekEndWeekday` plus a ready-to-say `phrase`
  ("Monday 2026-08-03 through Sunday 2026-08-09") on every resolution, single dates included, and
  the same on the weekend-ambiguous `alternate` — the branch that asks the agent to read BOTH ranges
  to a person. Built through one helper each so a future return site cannot ship a date without its
  weekday. The labels are constants by construction (weekStart IS a Monday), which is the point:
  handing over a value the model could in principle derive is precisely how you stop it deriving.
  **Verification lesson:** a live turn that produces the right answer does not prove the fix fired.
  Check the mechanism — here, `query_audit` showed the SQL never selected the column. Right answer,
  wrong reason, and the next week it would have been the 2026-08-06 "Monday the 4th" bug again.
- **A HOOK plugin is not installed until the GATEWAY's startup line says so (2026-08-06).** Three

- **`openclaw plugins install` — the VENDOR's own CLI — trips the config-hash trap (2026-08-06).**

- **DOCTRINE — the manager is NEVER a verification layer for dates (owner decision, 2026-08-11).**

  added late in AGENTS.md is probably invisible; verify with the head/digest/tail model before
  trusting it.** Trimming AGENTS.md is the real fix and is still owed.

- **Money's structure in the spine is load-bearing for FUTURE BUSINESS ANALYTICS** (user
  constraint 2026-08-19). `money_events` is not L1/L2/L3 — it is a ledger ALONGSIDE L2, FK'd into
  it, with evidence links back to L1. **L2 = nouns (what exists now); the ledger = verbs (what
  happened, in order)** — state is folded, never stored, and the `completed → invoiced → paid`
  status hops are derived by `syncJobStatusForMoney`, never hand-advanced. The two are
  conceptually separate but must be **read together**, and that coupling is already enforced
  structurally, not by convention: `job_id not null references jobs(id) on delete restrict` (no
  orphan either way); `v_money_events` joins job + customer onto every row so agent SQL cannot
  select a bare amount; and every accessor is job-keyed (there is deliberately no "list all money
  events"). **THE RULE for any analytics work: aggregate the SUMMARIES (`summarizeMoney` per job),
  never the rows.** Hand-rolled SQL over `money_events` must re-implement four things the fold
  already handles, and silently lies if it misses one: direction is by `kind` and never sign
  (`amount_cents >= 0` is a DB check, so cross-kind `sum(amount_cents)` is nonsense — **cost kinds
  newly enable this mistake**); negated rows (voids/corrections) stay in the table forever;
  `currency` is a defaulted column, not a guarantee; and `lastEventAt` scans ALL events including
  negated ones. Consequence: **costs belong as new KINDS inside `money_events`, never a separate
  cost table** — new kinds are provably inert in existing revenue math (the fold is kind-additive)
  and inherit the FK, the joined view, the accessors and negation semantics for free.

  the repo"). Corollary: s2 being freshest is *how this hid* — audit a NON-s2 seat, or all of them.
- **A per-seat exemption exempts that seat from every LATER fix, not just the one it was written
  for.** s3's tool-deny carve-out meant nothing ever re-ran `wire` there, so it sat on July doctrine

**Working in a second worktree (local Supabase stacks):**
- **`npx supabase stop` targets the `project_id` in the CURRENT directory's
  `supabase/config.toml` — so running it from a worktree that never had
  `scripts/second-stack.sh` applied STOPS THE PRIMARY STACK, not that worktree's.**
  `second-stack.sh` leaves the rewritten `project_id`/ports *uncommitted*, so any worktree where
  that edit was reverted (or never made) reads `project_id = "TradesDatabase"` and the CLI
  cheerfully stops the main checkout's stack out from under whoever is using it. Hit twice on
  2026-08-19, once while a concurrent session was mid-`npm test`. **Always
  `grep -m1 '^project_id' supabase/config.toml` before `supabase stop|start`**, and read the
  CLI's closing line — it names the project it acted on
  (`Local data are backed up to docker volume ... project=<id>`), which is the cheapest
  confirmation you stopped what you meant to. Recovery is `npx supabase start` from the main
  checkout; the volume-backed data survives a plain `stop` (only `--no-backup` discards it).
- **Concurrent local stacks are the top cause of phantom test failures on this machine.** Four
  stacks = 46 containers and the Docker VM pinned near 1200% CPU on a 14-core Mac; DB-backed
  suites then blow their 10s `beforeAll` / `pg.connect()` hook timeouts and fail in a different
  combination on every run. The tell is **failures that move between runs** and a suite time that
  balloons (33s → 135s for the same tree). Before believing any red suite, check
  `docker ps -q | wc -l` and per-stack CPU
  (`docker stats --no-stream`); a comments-only diff cannot break 15 tests. Stop stacks belonging
  to merged/abandoned worktrees — verify with
  `git merge-base --is-ancestor $(git -C <wt> rev-parse HEAD) origin/main` first.

**Tuning a constant (the nudge ladder, 2026-08-20):**
- `NUDGE_ESCALATE_HOURS` **48 → 24** and `NUDGE_DELIVERY_DEADLINE_HOURS` **24 → 18**. These ask
  DIFFERENT questions and had collided by accident: escalation is *how long do we wait for a
  PERSON*; the delivery deadline is *how long before we admit the MACHINERY is broken* (offboarded
  tech, recycled sandbox with a cleared `host_id`, rollback-frozen row). Nobody is ignoring us in
  the second case, so there is no patience to extend — **a gap nobody can even receive should reach
  the manager SOONER than one somebody is sitting on.** The deadline's floor is ~14h, not zero: the
  7am-7pm ask window holds an evening gap overnight (12h; 13h on a DST fall-back night), and below
  that we start telling the manager "never delivered" about a question that was seconds from being
  asked. A window that ever excludes whole DAYS must move that number FIRST.
- The evidence for 24h came from the PLANNER, before the code changed: across three shadow ticks on
  one real pilot gap it chose to escalate at 24h and argued it from job size ("a routine 60-min
  visit follow-up should not sit unanswered for a full day"). 48 was never reasoned about.
- **Retuning a constant is retroactive.** The pilot row was already 24.8h old, so the first sweep on
  the new code escalated it 14 seconds after the container came up — a day earlier than its own
  clock would have. Check what is already past the NEW threshold before shipping a shortened one.
- **TEST ROT — hit three times in one day.** Fixtures that hardcode hours (`49h`, `25h`, `22h`) were
  each chosen to sit on one side of a boundary; retune the constant and the boundary slides out from
  under them, and a test named for a case silently stops testing it. Derive fixture timestamps FROM
  the constant. Same shape as the weekday-guard bomb below. The check that catches it: flip the
  constant and confirm the suite is still green *for the right reason* — then break the behaviour
  and confirm it fails.

**Calling the model from the spine:**
- **GLM-5.2 thinks BY DEFAULT, so a small `maxTokens` truncates the FIRST turn — not the answer,
  the whole call.** Measured 2026-08-20: the team-lead planner at `maxTokens: 4096` with
  `reasoningEffort` unset returned `finish_reason=length` on turn one and produced no plan at all.
  The truncation guard caught it (that is what it is for); the caller simply could not run. Fixed
  with `reasoningEffort: 'low'` + 8192 — deliberately NOT `'none'`, which is right for a
  forced-JSON extraction and wrong for a call whose entire job is judgment.
  **Three shipped callers carry the same latent risk, unmeasured:** `src/calls/classifyCall.ts`
  (maxTokens **256**), `src/email/classify.ts` (**256**), `src/writePath/extract.ts` (1024). They
  work today because their prompts are short; a long email or transcript is the input that trips
  them, and the failure is a thrown error, not a degraded answer.

**Working on the agent boxes:**
- **A tool DESCRIPTION change is not deploy-only; a result-side field is.** Gateways cache
  `tools/list` per process, and descriptions are part of that payload — so editing one needs
  `nemoclaw <s> gateway restart` before any agent sees it, while adding a field to a tool's
  *result* (PR #83's grounding riders; the 2026-07-31 per-stop `mapsUrl`) goes live on deploy
  alone. A full box wire re-run is only needed when the change also touches AGENTS.md contract
  text or the pinned tool NAMES — a pure description edit touches neither. **And the restart is
  per TIER, not fleet-wide:** a tool filtered off one surface only forces restarts on the tier
  that carries it. Worked example (2026-07-31) — the `get_schedule` rewrite changed that tool's
  description, but `get_schedule` is filtered out of `MANAGER_TOOLS`, so *technician* sandboxes
  needed the restart and the manager side, whose change was result-only, was live the moment
  Render deployed. Getting this backwards costs either a stale fleet or needless restarts.
  **Amended 2026-08-04, after the tool-search rollout (PR #99):** under `tools.toolSearch` a
  description is no longer only the parameter surface — it is the **discovery surface**. The
  model's loaded tool list is just `tool_search`/`tool_describe`/`tool_call`; every spine tool is
  a catalog entry it has to *find*, by matching against that description text. So a description
  edit now changes both what the agent can learn about a tool and whether it locates it at all,
  and the gateway's per-process `tools/list` cache still gates when either takes effect. The
  matching failure is silent and total — that is exactly how `resolve_date` stopped being called
  (§0j in `bootstrap-box.sh` teaches the route explicitly as the fix). **Any tool whose
  description you rewrite inherits that exposure**; `get_schedule` was rewritten on 2026-07-31
  and has no §0-style block of its own, so "the agent never called it" is a live failure mode to
  rule out before blaming the tool.
- **A sandbox can hold a badge the doorman no longer knows — and nothing says so.** Found on s5
  2026-08-04: every spine call returned the doorman's flat `badge not authorized`, while
  `badges.json` held a live, non-revoked entry for that very person (`ben-shelton`). The sandbox
  was simply carrying an OLDER badge — the pull regenerates `badges.json` wholesale from the
  roster, so a rotation orphans whatever the sandbox still has. There is no error surfaced to the
  operator, no unhealthy status, and the container/gateway both report healthy; the bot just
  cannot reach any tool. **Diagnostic (verified, fingerprints only — never print plaintext):**
  fingerprint the badge from BOTH `/sandbox/.openclaw/openclaw.json`
  (`.mcp.servers["trades-spine"].headers.Authorization`, strip the `Bearer ` prefix) and the
  running gateway's `/proc/<pid>/environ` `TRADES_SPINE_BADGE`, then test
  `jq --arg f "$FP" 'has($f)' /etc/doorman/badges.json`. Both fingerprints matching each other but
  absent from `badges.json` = orphaned badge, and it also proves a gateway restart did not cause
  it (the file and the live process agree). Fix is server-side `rotate-badge` → next pull mints
  into `/root/pending-badges.jsonl` → install as the provider credential → **container** restart
  (a gateway restart is not enough; creds inject at container launch). Check this BEFORE
  debugging any "the agent isn't using tool X" report on a specific sandbox.
- **The doorman is ONE shared process — an unhandled stream `error` anywhere in its request
  flow kills every sandbox's in-flight MCP call at once.** Bitten 2026-08-04: an upstream TLS
  reset mid-SSE fired `upReq`'s error handler *after* the response head had been relayed; its
  unconditional `res.writeHead(502)` threw `ERR_HTTP_HEADERS_SENT` and the whole process exited.
  `Restart=always` brings it back in ~5s, so the only visible symptom is a climbing
  `restart counter` in `journalctl -u doorman.service` — check that counter before trusting "the
  doorman is fine". Fixed 2026-08-11 (headersSent guard, `stream.pipeline` instead of bare
  `pipe`, client-disconnect teardown of the upstream leg); `src/control/doorman.test.ts` now runs
  the REAL `Box_Setup_Stuff/doorman.mjs` against a stub upstream and replays every one of these
  deaths. Two docs embed verbatim copies of the file (`doorman-runbook.md`,
  `doorman-nemoclaw-setup-guide.md`) — they must stay byte-identical to it; the runbook's copy
  drifted once (2026-07-06→08-11) and kept handing out the crash-prone pre-relay code.
- **Credentials inject into a sandbox's process env at container launch ONLY.** Any provider
  credential write (badge install/rotation, token change) needs a container restart to take
  effect. This exact mechanism silently killed Judy's spine MCP for 4 days (badge in store,
  absent from env).
- **A manual `docker restart` of a long-running sandbox can crash-loop on
  `invalid token: ExpiredSignature` (hit 2026-08-12, s2 token handover).** The gateway mints each
  sandbox's JWT ONCE at create (`~/.local/state/openshell/docker-sandbox-tokens/…/sandbox.jwt`,
  TTL ~30d from `openshell-gateway.toml`); the running supervisor refreshes it in memory only and
  never rewrites the file. Restart the container after the on-disk token expires and it boots
  into `Policy fetch failed … ExpiredSignature` with "static token sources cannot rebootstrap
  automatically" — the revive unit then flaps in `activating auto-restart`. Fix:
  `sudo systemctl restart sandbox-token-medic.service` (re-mints from the gateway's signing key
  and restarts the container; script header at `/usr/local/sbin/sandbox-token-medic.mjs` has the
  full story — it exists because a 2026-07-05 box reboot hit the same class). Side effect: run
  without `NO_RESTART=1` and it also bounces every OTHER sandbox whose on-disk token is expired,
  healthy or not (s3 and s5 took ~10s blips as bystanders on 2026-08-12). So: before any manual
  container restart, run the medic (or check the token's `exp`) — the credential-restart rule
  above still applies, it just needs a valid sandbox token to survive the restart.
- **NEVER change a sandbox's `openclaw.json` with `openclaw config patch`.** It writes the file
  but does NOT update nemoclaw's `.config-hash`, so the next `gateway restart` fails
  `GATEWAY_UNSAFE_CONFIG_PATH` and leaves the gateway DOWN (3 bots went down learning this on
  2026-07-30). Two extra teeth: run as root via `docker exec` and the file ends up `root:root`,
  which the gateway also refuses (`chown sandbox:sandbox` + `chmod 660` to fix); and without a
  login shell `OPENCLAW_HOME` is unset, so the patch silently lands in `/root/.openclaw/` and
  changes NOTHING — it still prints "Applied N config update(s)". **Always verify by reading
  `/sandbox/.openclaw/openclaw.json` back, never trust the success message.**
  Use the gateway-mediated recipe instead (already in `bootstrap-box.sh`, heartbeat + tool-trim
  blocks): `nemoclaw <s> download` → edit with `jq` → `upload` → write `.config-hash` →
  `chmod 660` → `gateway restart`. If a gateway is already stuck this way,
  `nemoclaw <s> doctor --fix` then restart clears it.
  **The ownership tooth bites specifically on ATOMIC REPLACE (learned 2026-08-03 — s5/s6/s7/s8 all
  went down for ~2 min).** A root-side write *in place* (`open(path,"w")`) truncates the existing
  inode and **keeps** `sandbox:sandbox`, so it works. Rewriting the same script to be "safer" —
  write `path.tmp`, then `os.replace()` — creates a **new inode owned by root**, and
  `shutil.copymode()` copies the mode but **not the owner**, so `ls` still shows `-rw-rw----` and
  nothing looks wrong. `chmod` is not a substitute for `chown`: after ANY root-side write, run
  `chown sandbox:sandbox` and check the **owner** column, not just the permission bits, before
  restarting. The failure is at least loud and instant — every restart returns
  `GATEWAY_UNSAFE_CONFIG_PATH`, and chown + restart is the whole recovery.
- **FOURTH tooth, SOLVED 2026-08-12 — the "something keeps resetting s7's perms" mystery was
  our own deploys plus a silent lost race.** Evidence: s7's `config-audit.jsonl` shows EVERY
  openclaw config write (`config patch`, `plugins install`) creating a fresh `openclaw.json`
  inode at **0o600** — vendor secure-default, six for six entries (`previousMode 660 →
  nextMode 600`; the 2026-07-31 one also left it `root:root`), and every one of those writes
  was our own rollout tooling. nemoclaw anticipates this: `normalize_mutable_config_perms.py`
  restores 660/2770 after each command — but it **fail-closes by design** (`UnsafeTree`; its
  stability key includes `st_mtime_ns`) when ANY file in the tree changes mid-walk, and the
  failure is a swallowed "cleanup exit 1" in stderr. A busy gateway loses that race; s7 (the
  busiest test box) lost it three times (2026-08-06, 2026-08-12 ×2), each ending in
  `GATEWAY_UNSAFE_CONFIG_PATH`. Fault-injection on s6 (set 700/600, run the normalizer) proved
  the repair path itself sound — the failures were the race, not the script. Fix (PR #126):
  the bootstrap's guard-install block now restores `chmod 2770` + `chmod 660` +
  `chown sandbox:sandbox` DETERMINISTICALLY between `plugins install` and `doctor --fix` (a
  root chmod on two named paths cannot lose a race), and `verify` gained a per-sandbox perms
  tripwire so a lost race can never again be silent. Upstream-worthy: a fail-closed security
  check whose failure is invisible is half a mechanism.
- **`nemoclaw rebuild` can destroy the sandbox's device private key** (vendor bug: the
  state-snapshot sanitizer replaces `privateKeyPem` with `[STRIPPED_BY_MIGRATION]` in the
  LIVE identity). Symptom: endless device-pairing loop, no Telegram polling, no MCP. Detect:
  `grep STRIPPED_BY_MIGRATION .../identity/device.json`. Back up identity files around any
  rebuild; prefer `gateway restart` (safe) over rebuild wherever possible.
- **The placeholder versioning trap:** the stock start script freezes credential placeholders
  to a versioned form; a later provider write strands them → dead Telegram bridge after
  restart. The boot self-heal never runs on the new-generation stack. After any provider
  credential write, confirm placeholder forms are canonical before restarting agents.
- **`nemoclaw onboard`/rebuild resets the gateway inference route** to the NVIDIA free-tier
  default (rate-limited, wrong model). The medic timer re-asserts DeepInfra within 5 min; if
  agents act "dumb"/throttled right after an onboard, that's why.
- **Tool VOCABULARY lives in three places, and one of them self-reapplies.** Renaming or
  adding an agent-facing tool means: (1) the MCP tool defs (gateway-cached `tools/list` →
  fleet restarts), (2) the living docs (`docs/nemoclaw-tech-agent.md` + the Box Setup Stuff
  sync rule), and (3) **the heredoc template blocks in `Box_Setup_Stuff/bootstrap-box.sh`**

  `Box_Setup_Stuff`. (Caught in the 2026-07-25 cancel-vocabulary plan review.)
- **There is NO per-tool allowlist file** in the sandbox configs, whatever older docs imply.

- **The Telegram sender allowlist lives in TWO places** (rendered `openclaw.json` +
  `.config-hash`, and source `sandboxes.json` `allowedIds`) — a durable change writes both,

- **Never health-check via `nemoclaw <s> agent`** — it injects into the person's LIVE

- **Trust box evidence over vendor status pages** (DeepInfra stayed green through two real
  outages). Both-providers-dead alarm → check the DeepInfra balance (HTTP 402) first.
- **DeepInfra balance runs out roughly monthly and NOTHING alerts on it** — 2026-07-11,

  `openshell inference set -g nemoclaw --provider deepinfra-prod --model zai-org/GLM-5.2` —

- Small but sharp: non-interactive ssh lacks `nemoclaw` on PATH

- **`/hooks/agent` (the gateway's HTTP webhook) CANNOT drive an agent turn on this box.** It
  admits the request (`200 {"ok":true,"runId":…}` in ~30-60ms) and then **skips the run**:
  hook runs execute through the **cron** runner, which preflights any provider whose `baseUrl`
  is loopback / private-network / `.local`
  ([cron docs](https://docs.openclaw.ai/automation/cron-jobs)). OpenShell's endpoint is
  `https://inference.local/v1`, so it is probed — and the probe does a **direct `getaddrinfo`**
  in a namespace with **no public DNS at all** (`api.deepinfra.com` does not resolve either;
  everything egresses via the proxy at `10.200.0.1:3128`, which does the resolving). Real model
  calls work precisely because they go through that proxy, so the preflight is a **false
  negative on a working provider**:
  `Agent cron job uses inference/z-ai/glm-5.2 but the local provider endpoint is not reachable
  at https://inference.local/v1. Skipping this cron run … getaddrinfo EAI_AGAIN inference.local`
  Tested with `deliver:false` **and** `deliver:true` — identical skip, 16 minutes apart (so the
  5-minute reachability cache had expired; `EAI_AGAIN` is nominally "temporary" but is permanent
  here). `deliver` cannot help: the preflight is the entrance, `deliver` is the exit. The docs
  state the preflight **cannot be disabled** (`--fallbacks ""` only narrows the walk to the
  primary, which is the failing candidate). **Use the CLI gateway path instead.**
  **Latent production risk from the same root cause:** any *isolated agent cron job* a manager
  schedules would be silently skipped — and skipped runs do not increment execution-error
  backoff by default, so nobody is told. Nothing is broken today (s2 has no cron jobs and zero
  occurrences), but §0h doctrine actively invites recurring work ("run the freeze every Friday
  morning" is named as the canonical legitimate recurring job). Mitigations:
  `failureAlert.includeSkipped` to surface repeated skips, or give the inference provider a
  `baseUrl` that is not loopback/private/`.local` so it stops being preflighted at all.

**A date label built from an offset-less string is a wrong sentence the date rail cannot catch
(guarded 2026-08-25).** Every human-facing time in the ladder comes from one of two formatters —
`clockLabel` (`src/teamLead/planner.ts`) and `wallClockLabel` (`src/jobs/watchers.ts`) — which
parse a string and format the result in a named zone. Per ECMA-262 a date-time **with** an offset
is absolute, and one **without** is read on the host's clock, so an offset-less input silently
means a different instant on a dev laptop than on Render: `2026-08-24T07:00:00` renders 7:00 AM in
UTC, 2:00 PM from an LA host, and **Sunday 10:00 PM** from Tokyo. Nothing in the repo produced that
shape — `naiveLocalISO` appends `.000Z` for exactly this reason, and PostgREST returns `+00:00` —
so the convention held while being invisible at every call site. The names pointed the other way:
the parameter was literally `naiveIso` and the header said "a naive-local string", which is
precisely the input that shifts; a hand-built test harness reproduced the shift by believing them.

Why it outranks a formatting nit: **these labels are the planner's date-safety mechanism.**
`buildGapView` hands them to the model as the only date vocabulary it may use, and
`cleanPlannerText` refuses any note containing a date outside that list. The rail therefore proves
the model **copied** the string — never that the string was **right**. A shifted label is laundered
into a confident, rail-approved sentence to a technician or a manager, and a one-day rollover is
invisible to every existing check. This is the same shape as the humans-never-check-dates rule:
date safety has to be machine-side on **both** ends.

The rule is now explicit rather than conventional: `parseAsUtc` (`src/schedule/availability.ts`)
reads an offset-less date-time as UTC and passes everything else — offset-stamped, date-only,
unparseable — to `Date.parse` untouched. Both formatters and all three zone helpers
(`localDateISO`, `localDayOfWeek`, `localTimeHHMM`) route through it, and the tests flip
`process.env.TZ` across UTC / LA / Tokyo so the invariant fails on a UTC CI box too, not just on a
non-UTC laptop. **Explicitly not affected, and left alone:** the naive-vs-naive comparisons in
`watchers.ts` and `nudgeKinds.ts` parse both sides the same way so any offset cancels, and
`MAX_UTC_OFFSET_MS` already absorbs ±14h of slop.

### The build order, revised (2026-08-22)

**Build order, revised 2026-08-22 (third revision).** Two user rulings reshaped it.

*Ruling 1 — closing is the planner's job.* The sweep runs every 5 min and the planner every 30, so
the fast deterministic thing always won the race, which is backwards from the AI-manager premise.
Only `filled` ("did this answer the question?") is a judgment; `moot`, escalate, expire and the
delivery caps are facts. `filled` therefore stops closing and the planner's `close` becomes the
normal end of a gap. Three things fall out free: two-gaps-one-job becomes judgeable (the gap stays
open, so the planner sees the answer), the planner gains a feedback loop it never had, and
`record_filled` is redundant because `basis:'record'` vs `basis:'evidence'` already carries the
answered-vs-filled distinction. Fail-safe = **one working day**, anchored to the existing
escalation deadline rather than a new constant (already 24h default, planner-adjustable, 48h cap,
and sitting exactly where a false escalation would land); it fires only when no APPLIED planner
*judgment* exists in 24h. **Cross-phase hazard:** the continuity phase writes `unmentioned` rows
with `outcome:'applied'`, so a naive liveness test would be true for every gap on every tick and
the fail-safe would silently never fire — count only real verbs.

*Ruling 2 — the planner should read basically everything.* **RESOLVED 2026-08-23 (④, plan
`thoughts/shared/plans/2026-08-23-the-brain-can-look.md`):** `v_captures` (labeled retraction
trail, sensitivity unfiltered per the same-day ruling), `v_visits` (the note→job bridge — a note's
own `job_id` is NULL by design, the durable link is the visit), `v_nudges` and `v_review_items`
joined the surface: twelve views. `nudge_decisions` stays deliberately view-less (the catalog is
shared with the manager's `query_spine`). Historical statement of the gap, kept for the reasoning:
`spine_read` exposed 8 views and **none covered `raw_captures`, `nudges` or `review_items`** — the
planner could not read what anyone said. This is why the read surface moved IN FRONT of the memory
work: the memory design is "push the keys, pull the content", and the pull half does not work if

  and ~7 treated factual silence reporting ("has not responded") as blame though it is
  deliberately absent from the firm's blame vocabulary. 27 of 34 judged failures across both
  arms were phantom; the flagship "GLM over-claims" specimen (SMOKE-1: "no visit has been
  logged") was DB-verified truth. Rule: any LLM judge grading claims must be handed the same
  evidence the graded model had (transcript or verified-fact digest), and blame standards
  must be pinned to the firm's vocabulary list, not the judge's instinct. Also caught:
  substring claim checks can self-negate ("hasn't answered" contains "answered" — FC-08),
  and a scenario can fail both arms because it was mis-authored, not because the models
  erred (MG-07). Full verdicts: docs/agentic-eval-rejudge-2026-08.md.

### The ask shape — one message may cover several gaps, and the answer keeps its link (2026-08-25)

Built on `feat/the-ask-shape`, on top of the one-call collapse (PR #179). Four phases, all landed
in the branch; the six-seat doctrine refresh is the only step left and it is user-gated.
Plan: `thoughts/shared/plans/2026-08-25-the-ask-shape.md`.

**What changed, in one line each.** ① A gap closed on a quote now records WHICH capture answered
it, derived at close time from the citation the planner already had to prove. ② `nudges` gained
`ask_group_id`, so several gaps can ride out as ONE message. ③ The planner names the group itself
(`nudgeIds`) — code enforces coherence, never grouping policy. ④ A recorded field note hands the
seat agent back `openQuestions`, so it can follow up while the technician is still on the phone.

**The facts worth keeping:**

- **`ask_group_id` holds the LEAD gap's own id, not a fresh uuid.** The lead is then
  self-identifying (`id = ask_group_id`), so `sessionId: nudge-<lead>`, the box's sent-marker and
  the `(re: …)` anchor all name the gap the planner actually chose. Two earlier drafts disagreed
  about who the lead was ("the `nudgeId` field" vs "earliest-created") — they diverge the moment
  the planner does not pick the oldest gap.
- **Every member row stores the FULL grouped message in `question`.** Not a pointer, not a null.
  `nudgeQueue.ts`'s `if (!row.question) continue` tamper-freeze is the only thing between a
  malformed row and an infinite re-serve loop, and it stays untouched. The consequence is that
  anything reading `question` across a group must dedupe by TEXT.
- **The attribution stamp is an audit link, not a gate.** `attributeAnswerToGap` still declines to
  stamp when 2+ gaps are asked — code cannot tell which question a sentence answered. Batching
  lands squarely in that case, which is exactly why ① exists: the close-derived stamp comes from
  the quote the planner cited, so a batched ask does not go dark.
- **The derived stamp requires a capture a badge-holder SPOKE** — a channel test
  (`technician_note|technician_voice|technician_photo`) AND a non-null ref. The ref alone is
  INERT as a guard: the phone worker stamps the sentinel `'phone-line'` and mail ingest stamps the
  MAILBOX OWNER's ref on a customer's reply, so both foreign shapes carry one.
- **`openQuestions` is deliberately UNFILTERED and can include what the person just said.**
  Attribution declines at 2+ asked, so no "which one did they just close" signal exists. Worse,
  `setNudgeAnsweredBy` does not change `status` and the watcher's activity auto-close needs
  `soleGapOnJob`, so **the list does not shrink as gaps are answered** — the same entries return on
  every subsequent note for that job. §0k judges against the whole conversation, not the last
  message. Reporting what is open is honest; guessing which one closed is not.
- **The follow-up loop has two halves and both had to be written down.** ASK without RECORD leaves
  the gap `asked` and the office re-asks the technician what they just said — §0k clause 1b.
  And the reply to a follow-up is a bare fragment ("about two hundred") that `matchIdentity` cannot
  resolve, so 1b must name the mechanism: `confirmed: {customerId}` with NO `confirmId` (the
  dispatch reads `confirmed` before the confirmId branch and one-shot commits). Without it the
  assistant asks the technician WHICH customer, seconds after recording one for them.
- **④b's zero-inference rule governs the ASK LEG ONLY** (user correction). The seat agent already
  reasons freely once a person replies, so a response-leg follow-up contradicts nothing.
  **Waking the planner on the answer event is RULED OUT** (user, 2026-08-25): a planner-written
  sentence dropping into a live conversation is two voices in one chat, and the planner holds no
  technician write tools if it stayed in the session.

**Traps this build hit, in the order they bit:**

1. **A two-line `## ` heading in the §0k block would have corrupted all six seats.** The block is
   installed by a delete-then-append `awk` that deletes from `/^## Questions and items from the
   office/` to the NEXT `^## ` line — so a second heading line orphans into every AGENTS.md on
   every refresh, and `extractDoctrine` reads the section as empty. Caught by
   `src/eval/doctrine.test.ts`, not by review. **Keep §0k headings on ONE line.**
2. **`doctrine.test.ts` pins SECTIONS, not CLAUSES.** Deleting a clause from §0k failed no test
   until this build added a body assertion. The block is the only instruction the six seats have.
3. **`vitest.config.ts:11` sets `fileParallelism: false`.** Do not reject a test approach on
   "it would poison concurrent files" — nothing runs concurrently. The real objection to a
   `REVOKE`-based failure injection is durability: a restore skipped by a crash breaks the local
   stack for every later file and the next run. `vi.mock` in its OWN file is the clean route, and
   it reaches `src/mcp/server.ts` through the `export * from './nudges.js'` barrel.
4. **Pre-existing, still live:** if `docker exec … grep -q` at `bootstrap-box.sh:1018` fails for any
   reason OTHER than the block's absence (a transient docker error), the delete is skipped and the
   block DOUBLE-APPENDS. No repo test can see it — `doctrine.ts` reads the script, not the seat.
   Audit with `grep -c '^## Questions and items' AGENTS.md` after any fleet refresh.
5. **Known efficiency cost, accepted:** `commitNote` now issues `listAskedNudgesForTechnicianJob`
   twice per recorded note with identical arguments, on the hottest technician write path. Halving
   it means having `attributeAnswerToGap` return what it read, which its `Promise<void>` pin rules
   out.

must read `203d9ae2c05b103cb378092fc27ce4ed` — two earlier values in the plan are superseded
drafts. Roll **s2 first** (the canary seat), then the fleet, then audit a NON-s2 seat.
