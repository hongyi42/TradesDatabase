# GLM-5.2 inference provider options — AWS / Google / Azure vs. DeepInfra

**Date:** 2026-08-14
**Question:** The fleet runs GLM-5.2 via DeepInfra. Is DeepInfra slow relative to alternatives, and do
the hyperscalers (AWS, Google, Azure) offer GLM-5.2 inference — and in what form (pay-per-token API
vs. bundled platform/GPU rental)?
**Method:** four parallel research agents, all claims verified against live vendor docs on 2026-08-14
(per the CLAUDE.md external-services rule). Speed numbers are Artificial Analysis 72-hour rolling
medians at a 10k-input-token workload — **perishable; re-measure before acting on them.**

## Headline findings

1. **DeepInfra is currently the slowest of 16 speed-tracked GLM-5.2 providers**: ~44 output tokens/sec
   median vs. ~180–320 tok/s for the fast tier. Its compensations: cheapest tier ($0.75 in / $2.40 out
   per 1M tokens), full 1M context, normal time-to-first-token (~1.3 s).
   [AA providers page](https://artificialanalysis.ai/models/glm-5-2/providers)
2. **The fast GLM-5.2 hosts are specialist inference shops, not the big clouds**: Makora ~322 tok/s
   (NVFP4), Baseten-FAST ~216, Nebius ~215, Crusoe ~195, CoreWeave ~187, Together ~182. No AWS or
   Google endpoint appears in the benchmarks at all.
3. **Speed rankings churn hard**: Fireworks measured ~315 tok/s on 2026-07-01 and ~92 today; Together
   ~346 → ~182 over the same six weeks. A snapshot is not a basis for switching — trial with our own
   eval corpus. [DeepInfra blog 2026-07-01](https://deepinfra.com/blog/best-glm-5-2-max-api-providers),
   [digitalapplied 2026-07-03](https://www.digitalapplied.com/blog/glm-5-2-api-access-providers-price-comparison-2026)
4. **No extreme-speed option exists for this model**: Cerebras has no GLM-5.x (its GLM-4.7 preview is
   deprecated 2026-08-17), Groq and SambaNova carry no GLM at all.
   [Cerebras models](https://inference-docs.cerebras.ai/models/overview)

## The hyperscalers, one by one

### AWS — GLM-5 serverless yes; GLM-5.2 self-host only
- Bedrock serverless (pay-per-token) hosts exactly three Z.AI models: **GLM 5** (`zai.glm-5`,
  $1.00/$3.20 per 1M, 200K context, 128K max output, 11 regions, OpenAI-compatible endpoint,
  **no prompt caching, no cross-region profiles**), GLM 4.7, GLM 4.7 Flash.
  [Model cards](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards-zai.html),
  [pricing](https://aws.amazon.com/bedrock/pricing/)
- **GLM-5.2 exists on AWS only via SageMaker JumpStart self-hosting** — deploy the FP8 weights onto
  your own endpoint; sizing needs 8×H200 (`ml.p5en.48xlarge`, ≈ $73/hr ≈ $53k/month, third-party
  pricing). [What's-new](https://aws.amazon.com/about-aws/whats-new/2026/01/glm-5.2-fp8-nemotron-nano-12b-v2-glm-ocr-on-sagemaker-jumpstart/)
- No published or independently measured throughput numbers for Bedrock's GLM endpoints (Artificial
  Analysis does not benchmark them).

### Google — exiting the business
- GLM 4.7 / GLM 5 shipped as managed pay-per-token endpoints (`glm-5-maas` $1.00/$3.20, 200K context),
  but **Google deprecated its entire open-model pay-per-token program on 2026-07-21; every such
  endpoint retires 2026-10-21** (GLM, DeepSeek, Qwen, Kimi, Llama, gpt-oss alike). GLM-5.2 never got
  a managed endpoint and now never will.
  [Deprecations page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/deprecations/open-models)
- Surviving path is self-deploy on Vertex/Model Garden: 8×H200 `a3-ultragpu-8g` ≈ **$96/hr** (~3×
  the bare-GPU-rental market rate). [Vertex pricing](https://cloud.google.com/vertex-ai/pricing)
- Verdict: dead end for our use.

### Azure — the only hyperscaler with GLM-5.2 pay-per-token
- **`FW-GLM-5.2` is GA on Azure AI Foundry via "Fireworks on Foundry"**: serverless pay-per-token,
  full 1M context, OpenAI-compatible, prompt caching. Pricing (Data Zone Standard, per 1M):
  **$1.54 in / $0.15 cached / $4.84 out**. Deploy regions: 6 US regions (Data Zone) or global
  provisioned. [MS Learn doc](https://learn.microsoft.com/en-us/azure/foundry/how-to/enable-fireworks-models),
  [catalog](https://ai.azure.com/catalog/models/FW-GLM-5.2), pricing via Azure Retail Prices API.
- Caveats: it is Fireworks' infrastructure behind Azure billing ("Customer Data will be sent outside
  of Microsoft systems"); excluded from the EU Data Boundary; requires registering the
  `Fireworks.EnableDeploy` preview feature; default token-per-minute quotas are tight (429s reported
  on a fresh GLM-5.2 deployment — [MS Q&A](https://learn.microsoft.com/en-us/answers/questions/5942767/reliable-deployment-of-glm-5-2)).
- Speed proxy: the Azure endpoint itself isn't benchmarked; Fireworks direct measures ~92 tok/s
  today (mid-pack, ≈2× DeepInfra, ≈half the fast tier).
- Raw GLM-5.2-FP8 weights are also in the Foundry catalog (Hugging Face collection) for managed-
  compute GPU deployment — same self-hosting economics as AWS/Google, not interesting at our scale.

## "Inference only, or bundled with the platform?"

Both AWS and Azure sell the pay-per-token form as a standalone product: you need an account and
billing on that cloud (and on Azure, one admin feature-flag registration), but no other services —
it's an API key and an OpenAI-compatible endpoint, the same shape as DeepInfra. The bundled form is
the GPU-rental one (SageMaker / Vertex / Azure managed compute), which only makes sense at volumes
that keep a $50–70k/month machine busy. Google is keeping only the bundled form.

## Implications for the fleet (not decided — options only)

- Decode speed is a real latency lever for us: GLM-5.2 thinks by default, so a turn pays
  (thinking + reply tokens) ÷ tok/s. At 44 tok/s that dominates turn time; past fixes (tool-schema
  trim, Composio relay) addressed different terms.
- Any provider change = quantization and serving-stack change (DeepInfra serves fp4; most fast
  alternatives differ) → **re-run the date-eval corpus (94 replies) and spine-tool eval before
  switching**, and note the nemoclaw medic v4/v5 probe + balance-check doctrine are
  DeepInfra-specific.
- A hyperscaler's postpaid invoicing would eliminate the ~monthly DeepInfra prepaid balance-outs
  (single balance feeds evals + fleet; alerting gap already noted in engineering memory).
- Context caps on some fast hosts (262K at CoreWeave/Together) are far above current per-session
  usage but below DeepInfra's 1M — check §0d chunked-batching assumptions if adopting one.

### Repeat experiment (same evening): chance vs provider, S04/Q04/M09 × 4 fresh-world cycles each side

Tally including the original full runs (n=5 per scenario per provider):

| Scenario | Nebius fails | DeepInfra fails | Verdict |
|---|---|---|---|
| S04 fabricated-link | 1/5 (full run only) | 0/5 | chance — never recurred |
| Q04 runaway stream | 1/5 (530s, full run) | **1/5 (260s, cycle 4)** | **model-level, NOT provider-specific** |
| M09 missed booking tool | 2/5 (same signature twice) | 0/5 behavioral (but 1/5 infra: a **938s** stall, cycle 3) | weak Nebius lean, not significant (p≈0.44) |

Key reversal: **DeepInfra produced the same runaway/stall pathology within 4 cycles** — a 260s
Q04 runaway and a 938s M09 harness-or-provider-failure. The runaway-reasoning failure mode is
GLM-5.2 itself (empty-completion / thinking-loop family, already known to this stack), not a
Nebius serving defect. Aggregate same-evening accuracy: Nebius 67/71 (94.4%) vs DeepInfra 69/71
(97.2%) — comparable; no clean quality gap at this sample size. Mechanism note for the 530s
stream: all tokens were thinking-channel (visible reply empty); the liveness watchdog only kills
*silent* streams (30s idle), so a chatty runaway lives until the total-turn budget.

|---|---|---|

**Accuracy: contaminated by a midnight straddle — report headline (54%) is VOID.** Run started
23:07 PDT (staleness guard legitimately passed); question D11's ssh transport hung for **71
minutes** (exit 255) — the AGENT had answered correctly in 9s, run.mjs salvaged the reply from
the trajectory as designed — pushing the remaining 59 questions past firm-local midnight, where
they were graded against Friday-anchored truth while the agent (correctly) answered for
Saturday (T10: "today is the 14th, right?" → "Nope — Saturday the 15th", right on the wall
clock, wrong to the manifest). **Validly-graded pre-midnight slice: 34 questions — 30 correct,
0 wrong, 4 needs-adjudication (P18–P21, the same adjudication class v3 scored correct).**

**Two harness gaps found:** (1) the stale-manifest guard checks only at START — nothing aborts
a run that CROSSES firm-local midnight; (2) run.mjs has no per-question ssh timeout, so one
wedged transport ate 71 min. Both are small fixes in scripts/date-eval/run.mjs.

**D11 is NOT a Nebius or model failure** — inference completed in 9s; the hang was the ssh/CLI
channel after completion. No runaway-reasoning events were observed through the gateway in 93
questions (gateway 60s timeout + the run's pace bound it regardless).

**Standing recommendation:** one clean evening-regime re-run (start well clear of midnight)
before the provider decision; evidence so far — spine 59/59, valid-34 clean, ~45% faster agent
turns — is consistently pro-Nebius.

## Follow-up (2026-08-14): Kimi K3 as an alternative model

- Kimi K3 (Moonshot AI): released 2026-07-16, weights 2026-07-27. 2.8T total params / 104B active,
  1M context, natively multimodal, Kimi Delta Attention. Largest open-weight model to date.
  [Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/moonshot-releases-2-8-trillion-parameter-kimi-k3),
  [Kimi platform docs](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart)
- **Price is effectively uniform at $3.00 in / $15.00 out per 1M** (Moonshot's list price; 10 of 13
  OpenRouter endpoints match it exactly; small discounts: Morph $2.80/$14.00, DeepInfra and
  DigitalOcean $2.85/$14.25). vs. GLM-5.2 on DeepInfra ($0.75/$2.40) that is ≈4× input / ≈6× output.
  [OpenRouter endpoints API](https://openrouter.ai/api/v1/models/moonshotai/kimi-k3/endpoints)
- **Speed (AA 72h medians, 2026-08-14):** Makora 155 tok/s, Parasail 148, Nebius 137, Modal 130,
  Baseten 117 (TTFT 0.96s, the best); AA reports ~4× spread across 12 tracked providers (slowest
  ≈ 39 tok/s). Top end is *slower* than GLM-5.2's fast tier (180–320) — the model is much bigger.
  [AA providers](https://artificialanalysis.ai/models/kimi-k3/providers)
- DeepInfra serves K3 at **bf16 with a 16K max-output cap** — the cap is a problem for a thinking
  model. Baseten caps output at 262K; Morph/Modal/Wafer allow 1M.
- Hyperscalers, same pattern as GLM-5.2: **Azure yes via Fireworks on Foundry** (since ~2026-07-30,
  [TechNode](https://technode.com/2026/07/30/moonshot-ais-kimi-k3-reaches-enterprise-users-through-fireworks-on-microsoft-foundry/));
  **AWS self-host only** (SageMaker HyperPod/EKS guide, no Bedrock serverless — Bedrock stops at
  Kimi K2.5, [AWS blog](https://aws.amazon.com/blogs/machine-learning/deploying-kimi-k3-on-aws/));
  **Google no** (open-model MaaS program retiring).
- Fleet implication: this is a model switch, not a provider switch — every eval (date-eval corpus,
  spine-tool eval), AGENTS.md prompt, and latency doctrine is calibrated on GLM-5.2, and at $15/M
  output a thinking model raises per-turn cost ~5–6×.
